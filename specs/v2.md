# Energy Tracker — V2 Specification

**Version:** 2.0
**Date:** 2026-03-17
**Builds on:** specs/spec.md (MVP, Phases 1–6)

---

## Overview

V2 introduces multi-user support via NextAuth.js v5 (Auth.js). Each user gets their own isolated set of energy entries. Sign-in supports Google OAuth and email/password credentials.

---

## Goals

- Allow multiple users to track energy independently
- Protect all routes and API endpoints behind authentication
- Keep the existing UI and UX intact — auth should wrap the app, not reshape it
- Use NextAuth.js v5 (Auth.js) for self-hosted auth with no third-party service dependency

---

## Constraints & Assumptions

- NextAuth.js v5 (the `next-auth@5` / `auth.js` package) is the auth library
- Google OAuth and email/password (Credentials provider) are the two sign-in methods
- Auth.js requires its own database tables (User, Account, Session, VerificationToken) managed via `@auth/prisma-adapter`
- Existing MVP entries (created without a userId) will need a migration strategy
- The `lib/db.ts` service layer already exists — adding `userId` filtering is a natural extension
- Passwords are hashed with `bcryptjs`

## Phases

---

### Phase 1 — NextAuth Setup & Schema Migration

**Goal:** Install Auth.js, add the required database models, and add user ownership to EnergyEntry.

#### Tasks

1. Install `next-auth@5`, `@auth/prisma-adapter`, `bcryptjs`, `@types/bcryptjs`
2. Add Auth.js required models to Prisma schema (User, Account, Session, VerificationToken)
3. `userId` column is already on `EnergyEntry` from the initial V2 migration — make it a proper foreign key relation to `User`
4. Run migration
5. Create `auth.ts` in the project root — configure Auth.js with:
   - `@auth/prisma-adapter`
   - Google OAuth provider (`AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET`)
   - Credentials provider (email + bcrypt password check)
6. Create `app/api/auth/[...nextauth]/route.ts` — export `GET` and `POST` from `auth.ts`
7. Add environment variables to `.env` and `.env.example`:
   - `AUTH_SECRET` (generate with `npx auth secret`)
   - `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET`

#### Schema Additions

```prisma
model User {
  id            String       @id @default(cuid())
  name          String?
  email         String?      @unique
  emailVerified DateTime?
  image         String?
  password      String?      // hashed, null for OAuth users
  accounts      Account[]
  sessions      Session[]
  entries       EnergyEntry[]
}

model Account {
  id                String  @id @default(cuid())
  userId            String
  type              String
  provider          String
  providerAccountId String
  refresh_token     String?
  access_token      String?
  expires_at        Int?
  token_type        String?
  scope             String?
  id_token          String?
  session_state     String?
  user              User    @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@unique([provider, providerAccountId])
}

model Session {
  id           String   @id @default(cuid())
  sessionToken String   @unique
  userId       String
  expires      DateTime
  user         User     @relation(fields: [userId], references: [id], onDelete: Cascade)
}

model VerificationToken {
  identifier String
  token      String   @unique
  expires    DateTime

  @@unique([identifier, token])
}

model EnergyEntry {
  id             Int      @id @default(autoincrement())
  createdAt      DateTime @default(now())
  mentalEnergy   Int
  mentalNote     String?
  physicalEnergy Int
  physicalNote   String?
  userId         String
  user           User     @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId, createdAt])
}
```

#### Acceptance Criteria

- [ ] `next-auth@5` and `@auth/prisma-adapter` are installed
- [ ] All Auth.js required tables exist in the database
- [ ] `EnergyEntry.userId` is a non-nullable foreign key to `User`
- [ ] `auth.ts` is configured with Google + Credentials providers

### Phase 2 — Login & Register UI

**Goal:** Build sign-in and register pages.

#### Pages

| Route       | Description                                      |
| ----------- | ------------------------------------------------ |
| `/sign-in`  | Email/password form + "Sign in with Google" button |
| `/register` | Email/password registration form (creates User with hashed password) |

#### Tasks

1. Create `app/sign-in/page.tsx` — client component with email/password form that calls `signIn("credentials", ...)` and a Google button that calls `signIn("google")`
2. Create `app/register/page.tsx` — client component with a registration form that POSTs to a new `/api/auth/register` route
3. Create `app/api/auth/register/route.ts` — validates input, checks email not taken, hashes password with bcrypt, creates User in DB
4. Add Auth.js middleware (`middleware.ts`) to protect all routes except `/sign-in` and `/register`
5. After sign-in, redirect to `/`; after sign-out, redirect to `/sign-in`

#### Acceptance Criteria

- [ ] Users can register with email and password
- [ ] Users can sign in with email/password
- [ ] Users can sign in with Google
- [ ] Unauthenticated users are redirected to `/sign-in`
- [ ] Invalid credentials show an inline error message

---

### Phase 3 — Scope Data to Authenticated User

**Goal:** Ensure each user only sees and modifies their own entries.

#### Tasks

1. Update all functions in `lib/db.ts` to accept a `userId` parameter:
   - `createEntry(userId, data)`
   - `getAllEntries(userId)`
   - `getTodayEntry(userId)`
   - `updateTodayEntry(userId, data)`
2. Update all API routes to extract `userId` from `auth()`:
   - Return `401` if no session
   - Pass `userId` to service functions
3. Update server components (`app/page.tsx`, `app/history/page.tsx`) to get `userId` from `auth()` and pass to service functions

#### Acceptance Criteria

- [ ] API routes return 401 when called without a valid session
- [ ] User A cannot see or modify User B's entries
- [ ] Home page and history page only show the current user's data

---

### Phase 4 — Header & Session UI

**Goal:** Add user info and sign-out to the app navigation.

#### Tasks

1. Add a simple header to `app/layout.tsx` showing the signed-in user's name/email and a sign-out button
2. Sign-out calls `signOut()` and redirects to `/sign-in`

#### Acceptance Criteria

- [ ] Signed-in user's name or email is visible in the header
- [ ] Sign-out button works and redirects to sign-in

---

### Phase 5 — Data Migration & Polish

**Goal:** Handle existing entries without a userId, and document setup.

#### Tasks

1. Write a migration script to assign existing `userId = NULL` entries to the first registered user, or simply delete orphaned entries if the database is just test data
2. Update `README.md` with NextAuth setup instructions:
   - Google OAuth client setup (Google Cloud Console)
   - Required environment variables
   - Running migrations

#### Acceptance Criteria

- [ ] No orphaned entries remain
- [ ] README documents full auth setup
